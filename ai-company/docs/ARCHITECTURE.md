# 全体設計書（PHASE 0）

依頼書「AI社員型 SNS・note 売上最適化システム」の 42番で指定された10項目について、
現時点（開発開始前）の整理内容をまとめます。専門用語には都度説明を添えています。

最上位ゴールは常に **「note購入数・note売上を増やすこと」** で、
SNSの再生数・フォロワー数はそのための手段（中間指標）として扱います。

---

## 1. システムの全体構成

会社組織にたとえた3層構造にします。

```
【あなた（社長 兼 唯一のスタッフ）】
        │ 質問・確認・承認
        ▼
【AI社長】……全AI社員の分析結果を見て「今日やるべきこと1つ」を決める
        ▲
        │ 各担当の分析結果を報告
【AI社員 12名】……Instagram担当／TikTok担当／YouTube担当／note担当／
                lit.link担当／LINE担当／競合分析担当／投稿企画担当／
                台本改善担当／データ分析担当／売上導線分析担当／AI管理担当
        ▲
        │ 数字・動画・文章などの生データ
【データ収集層】……各サービスの公式APIから取得 ／ 取得できない項目は手入力・CSV取込
```

技術的には、次の4層に分けて作ります。

1. **データ収集層**：各SNS・noteなどからデータを集めてデータベースに保存する部分
2. **データベース（保存場所）**：集めたデータを蓄積する場所
3. **AI分析層（AI社員・AI社長）**：保存されたデータをもとに分析・判断する部分
4. **画面（UI）層**：あなたが見る・操作するダッシュボード

「後からSNSや商品を追加しやすくする」ため、Instagram専用・note専用のコードを直接書くのではなく、
「プラットフォーム」「投稿」「導線」「販売商品」という共通の型（データ構造）を先に決めて、
各サービスはその型に情報を当てはめる形にします（36番の要件に対応）。

---

## 2. 推奨技術構成

プログラミング未経験の方が扱いやすいことを最優先にしています。

| 項目 | 推奨 | 理由 |
|---|---|---|
| フロントエンド（画面） | 素のHTML/CSS/JavaScript（PHASE 0）→ 将来的に必要ならNext.js等へ移行検討 | ビルド作業（npm等）が不要で、ファイルを開くかコマンド1つで動く |
| バックエンド（裏側の処理） | Python（FastAPI） | 既存リポジトリと統一。比較的読みやすい文法 |
| データベース | SQLite（1つのファイルで完結） | インストール不要。バックアップ＝ファイルコピーで済む。将来PostgreSQL等へ移行可能 |
| AI分析エンジン | Claude API（Anthropic） | テキスト・画像・チャットに対応。動画は音声/字幕/フレーム抽出して渡す想定 |
| 自動実行（将来） | Renderのスケジュール実行 or GitHub Actions（定期実行） | 追加サーバー管理が不要 |
| ホスティング | Render（既存リポジトリで利用中） | 追加学習コストが少ない |
| 秘密情報管理 | `.env`ファイル＋`.gitignore` | 33番の要件どおりコードに直書きしない |

PHASE 0（今回）はダミーデータのみを使うUI試作品のため、バックエンド・データベースはまだ作らず、
画面（見た目と動き）だけを先に作ります。

## 3. 現時点で利用可能と考えられる公式API（要検証・要確認）

**重要**：以下は2026年1月時点の一般公開情報をもとにした「現時点の理解」であり、
実際にPHASE 1以降で実装する直前に、各社の最新の開発者ドキュメントで必ず再確認します。
「取れるはず」で実装しない、という34番のルールに基づき、断定はしていません。

| サービス | 公式API | 必要なアカウント種別 | 備考 |
|---|---|---|---|
| Instagram | Instagram Graph API（Meta for Developers） | ビジネス／クリエイターアカウント＋連携Facebookページ | 高度な権限はMetaの審査（アプリレビュー）が必要になる場合あり |
| TikTok | TikTok API for Developers（Display API等） | TikTokデベロッパー登録＋本人アカウントの認可 | 詳細な分析（流入経路など）は公式アプリ内のエクスポート機能に頼る可能性あり |
| YouTube | YouTube Data API v3 ／ YouTube Analytics API | Googleアカウント（チャンネル所有者） | 比較的整備されており取得できる項目が多い |
| note | 現時点で創作者向けの公開APIは確認できていません | ― | 手入力・CSV貼り付け・画面コピー貼り付けを基本の運用方法とします |
| lit.link | 現時点で公開APIは確認できていません | ― | 自分で発行する計測用リンク（UTMパラメータ）や外部の計測サービスとの組み合わせを検討 |
| LINE公式アカウント | LINE Messaging API（一部、配信・フォロワー数の統計取得を含む） | LINE公式アカウント（認証済み推奨） | メッセージ内リンクのクリック計測は、LINEの計測用リンク機能や自前のURL発行と組み合わせる想定 |

取得できない項目は、11番で決めた代替方法（手入力／CSV取込／貼り付け／外部計測リンク）で必ず補完できるように設計し、
「規約違反になりやすい強引なスクレイピング」には頼りません。

## 4. 各サービスで取得できる／できないデータ（現時点の想定）

### Instagram（比較的取得しやすい）
- 取得できそうなもの：投稿一覧、投稿タイプ、投稿日時、いいね数、コメント数、保存数、リーチ、再生数（動画/リール）、
  シェア数（対応投稿）、プロフィールアクセス数・フォロー増加などのアカウント単位のインサイト
- 取得できない／要代替：「どの投稿を見てプロフィールに来たか」の厳密な特定、外部リンク（lit.link）のクリック数（→lit.link側 or 自前計測リンクで補完）

### TikTok
- 取得できそうなもの：自分の投稿一覧、再生数、いいね、コメント、シェアなどの基本指標
- 取得できない／要代替：詳細な視聴維持率や流入経路などはTikTok Studio（アプリ内）からのCSVエクスポート／手入力で補完する想定

### YouTube / Shorts
- 取得できそうなもの：再生数、平均視聴時間、維持率、いいね、コメント、登録者増減、トラフィックソース（YouTube Analytics API）
- 比較的信頼できるAPIのため、PHASE 3で優先的に実装

### note
- 公式APIが確認できないため、基本は「note作成者ダッシュボードの数字を手入力・CSV貼り付け」で運用
- 将来的に規約上問題のない範囲でブラウザからの安全な取得手段が見つかれば追加検討

### lit.link
- 公式APIが確認できないため、「どのリンクが何回押されたか」は自前の計測用リンク（例：短縮URL＋UTMパラメータ）を経由させる方式を軸に検討
- lit.link自体の管理画面に統計があれば、その数字を手入力で補完

### LINE公式アカウント
- 取得できそうなもの：フォロワー数・増減、配信数、開封・クリックなどの統計（Messaging APIの範囲内）
- noteへの流入・購入への貢献は、LINE内リンクに計測用パラメータを付けることで間接的に把握する想定

## 5. データベース設計（概要）

PHASE 0では実装しませんが、PHASE 1以降で作成するテーブル（データの入れ物）の想定一覧です。
「将来SNSや商品を追加しやすくする」ため、`platforms`（媒体マスタ）や`products`（販売商品マスタ）を
中心に据え、個別サービス専用のテーブルを増やしていく設計にします。

- `platforms`：Instagram/TikTok/YouTube/note/lit.link/LINEなど媒体の一覧（将来Threads/X追加もここに1行足すだけ）
- `accounts`：どのアカウントを紐付けているか
- `posts`：投稿の基本情報（媒体、投稿日時、URL、種別、キャプション）
- `post_metrics`：投稿ごとの数値（投稿直後／24時間後／7日後／30日後のスナップショット）
- `post_analysis`：AIによる動画・サムネイル分析結果（良かった点／悪かった点／次回変えること）
- `content_ideas`：投稿企画データベース（ステータス管理）
- `products`：note記事などの販売商品マスタ（将来別商品追加に対応）
- `product_pages`：販売ページの内容・変更履歴
- `product_metrics`：アクセス数・購入数・売上のスナップショット
- `funnel_links`：lit.link・LINEなど導線のクリック計測
- `funnel_events`：SNS→プロフィール→lit.link→note→購入のステップ別イベント記録
- `line_broadcasts` / `line_metrics`：LINE配信と開封・クリック実績
- `kpi_snapshots`：日次のKPIまとめ（ダッシュボード表示用に集計済みの数字を保持）
- `ab_tests`：A/Bテストの設定と結果
- `competitor_accounts` / `competitor_posts`：競合分析用データ
- `anomaly_logs`：異常検知の記録
- `ceo_decisions`：AI社長が出した「今日の最優先」とその根拠の履歴（後で答え合わせをするため）

## 9. 将来的に問題になりそうな点

- **note・lit.linkに公式APIが無い**ため、手入力の手間が残る／データ更新のタイムラグが発生しやすい
- 各SNSの**API利用規約・審査・レート制限**は変更されることがあり、事前に「取れるはず」と決め打ちできない
- クリック計測を自前のUTMリンク等に頼る場合、**ブラウザのトラッキング防止機能**などで一部計測が漏れる可能性がある
- 「どのSNS経由でnote購入に至ったか」を**完全に一意に特定することは技術的に難しい**（推定・近似にならざるを得ない部分がある）
- 動画・画像のAI分析は**投稿数が増えるほど分析コスト（AI利用料）が増える**ため、分析頻度の調整が必要になる可能性
- 個人開発のため、**API利用料・AI利用料・サーバー費用**などの運用コストを定期的に確認する必要がある
- スクレイピング（無理な自動取得）に頼る設計は**アカウント凍結等のリスク**があるため、今回のシステムでは意図的に避けている
